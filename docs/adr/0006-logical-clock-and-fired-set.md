# ADR-0006: 時刻は単調時計からの論理時刻で持ち、通知は実行済みの集合で管理する

| 項目     | 内容       |
| -------- | ---------- |
| Status   | Accepted   |
| Date     | 2026-10-11 |
| Deciders | t1nyb0x    |

## Context

要件 FR-102 と NFR-001 は、`setInterval` の回数に依存せず、遅延を累積させず、30 分以上の再生でドリフトしないことを求める。FR-105 は、時間を戻しても過去のコールを鳴らし直さないことを求める。

ブラウザのタイマーは遅れる。見えていないタブでは 1 秒単位に丸められ、Chrome はさらに長く隠れたタブのタイマーを 1 分単位に間引く。タイマーの回数で時間を数えると、遅れがそのまま積もる。

## Decision

- **論理時刻は、毎回時計を読み直して計算する**。`logical = anchorLogical + (now() - anchorMono)`。`now()` は `performance.now()` (単調時計)。一時停止・シーク・同期のたびに、アンカー (`anchorLogical`, `anchorMono`) を付け直す
- **タイマーは「次に鳴らす時刻まで」の 1 本だけ**を張る。起きたら時計を読み直し、その時点までに来ている通知を全部処理し、次の 1 本を張り直す。タイマーが遅れても次の計算には影響しない
- 描画 (残り時間の表示) は `requestAnimationFrame` で別に回し、論理時刻を読むだけにする
- **通知は ID を持ち、鳴らしたか (または飛ばしたか) を集合で持つ**。シークや同期で時刻を進めたとき、飛び越えた通知は鳴らさずに「飛ばした」に入れる (要件 FR-105)
- 起きたときに予定より大きく遅れていたら、まとめて鳴らさず、遅れた通知を飛ばして再同期を促す (スリープからの復帰、FR-102)。`visibilitychange` でも同じ確認をする
- engine は `now()` と `setTimer` を外から受け取る。テストは偽の時計で回す

## Consequences

### 良い点

- タイマーがいくら遅れても、論理時刻はずれない (要件 11.3-5 を構造で満たす)
- シークの前後で「何が鳴るか」が集合の状態だけで決まり、テストしやすい

### 悪い点・受け入れるリスク

- 鳴る瞬間の誤差 (タイマーの遅れ、読み上げの立ち上がり) は残る。PoC で測り、許容値を決める (要件 14 章 6)

### 追従して必要になること

この ADR では決めず、仮の値で作って後から決めるもの。

| 項目                                     | 仮の値                                                          | 決める場所                          |
| ---------------------------------------- | --------------------------------------------------------------- | ----------------------------------- |
| タイマーを Worker で回すか               | Worker で回すと決めた (ADR-0013)                                | PoC-001 (RM-13)                     |
| 遅れて気づいた通知を捨てるしきい値       | 2 秒 (`lateToleranceMs`)                                        | PoC-001 (RM-13)                     |
| 時刻を戻したとき、鳴らし済みをどうするか | 操作で分ける (設計書 03 の「戻したとき」)。設定で切り替えられる | M2 の試作を実戦で使ってから (RM-32) |

決まったら新しい ADR を書く。

## Alternatives

- `setInterval(100)` で回数を数える: 要件で禁じられている。遅れが積もる
