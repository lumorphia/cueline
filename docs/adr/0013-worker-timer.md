# ADR-0013: タイマーは Web Worker の中で回す

| 項目     | 内容       |
| -------- | ---------- |
| Status   | Accepted   |
| Date     | 2026-10-11 |
| Deciders | t1nyb0x    |

## Context

ADR-0006 は、タイマーを Worker で回すかメインスレッドで回すかを PoC-001 で決めるとしていた。PoC-001 の結果 (`docs/spikes/poc-001-timer.md`):

- 見えている状態の Worker は、PC (Chrome 154、FF14 を動かしたまま) で 2 回とも p95 15ms 前後、最大 45ms 以内。iPhone (WebKit、Wake Lock) で p95 7ms (1 回だけ 1 秒の遅れ)
- メインスレッドのタイマーは、ウィンドウが全部隠れると、80 秒ほどで 1 分に 1 回しか起きなくなり、最大 60 秒遅れた
- 論理時刻の積もりは、実機の 15 分でも headless の 35 分でも無かった
- 隠れた状態の Worker は 2 件しか測れていない (24ms、44ms)

## Decision

- **エンジンに渡すタイマーは、専用 Worker の中の `setTimeout` にする**。メインスレッドのタイマーは使わない
- Worker は予定より少し前に起きることが多い (headless で 1 件あたり約 6 回)。Worker の中で自分の時計を見て予定まで待ち直し、メインスレッドに知らせるのは予定を過ぎてからにする
- 隠れた状態の Worker は、たくさんは測っていないまま採用する。大きく遅れても、エンジンが `lateToleranceMs` (仮の値 2 秒) を超えた通知を鳴らさずに再同期を促すので、黙って変な時刻に鳴ることは無い (03)
- `AudioContext` を動かしたままにする対策は、タイマーのためには入れない。Worker で足りるため

## Consequences

### 良い点

- ウィンドウが少しでも見えていれば、15ms 前後の遅れで鳴らせる。事前コール (`before`) の秒数に比べて十分小さい

### 悪い点・受け入れるリスク

- 隠れたタブでの Worker の挙動は、件数が少ない。ブラウザの版が変わって間引かれるようになっても、気づくのは利用者の報告か `onMissed` の警告になる
- iPhone で 1 回だけ 1 秒遅れた原因が分からない。`lateToleranceMs` を 1 秒より小さくすると、この遅れで通知が捨てられる

### 追従して必要になること

- `lateToleranceMs` は 2 秒のまま。PoC-002 (読み上げ) と合わせて見直す
- 画面の案内に「ブラウザのウィンドウを全部隠したり、タブを切り替えたりしないでください」を残す。隠れた状態を多く測ったら見直す

## Alternatives

- メインスレッドのタイマー: 全部隠れると最大 60 秒遅れる
- `AudioContext` を動かしたままにして間引きを緩める: Worker で足りるうえ、効くかどうかが端末とブラウザの版に左右される
