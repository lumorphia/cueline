**作成日：** 2026年10月11日

**開発組織：** Lumorphia

# 1. プロジェクト概要

## 1.1 背景

FINAL FANTASY XIV（以下FF14）の高難易度コンテンツでは、戦闘開始からの経過時間に応じて、さまざまなギミックが発生する。

特に絶・零式では、ギミックの発生タイミングを把握し、適切なタイミングで行動することが重要となる。

本サービスでは、あらかじめ定義したタイムラインに従い、音声による通知（以下、コール）を行う機能を提供する。

ゲームクライアントとの直接連携は行わず、ユーザーが任意に作成したタイムラインを読み込んで再生する、独立したWebアプリケーションとして開発する。

## 1.2 目的

ユーザーが定義したタイムラインに従い、指定した時刻に音声や画面表示による通知を行える環境を提供する。

主な目的は以下のとおり。

1. タイムラインに従った音声通知を実現する。
2. ユーザーによるタイムラインの作成・編集を可能にする。
3. 高難易度コンテンツを想定したフェーズ管理・時間補正に対応する。
4. 音声エンジンを自由に選択できるようにする。
5. 導入・運用コストを最小限に抑える。
6. 将来的なデスクトップアプリ化・オーバーレイ対応を可能にする。

## 1.3 想定ユーザー

主な対象ユーザーは以下とする。

- FF14の高難易度コンテンツに取り組むユーザー
- 自作タイムラインによる通知を利用したいユーザー
- タイムラインの作成・調整を行いたいユーザー
- VOICEVOXなどの音声合成エンジンを利用したいユーザー

なお、アプリケーションの基盤は特定のゲームに依存しない設計とする。

## 1.4 基本方針

- クライアント主体のアーキテクチャを採用する。
- 音声合成・再生処理は原則クライアント側で実行する。
- タイムラインは宣言的なスクリプトとして管理する。
- ゲームプロセス、メモリ、通信、ログへのアクセスは行わない。
- 初期リリースでは認証やサーバー側処理を必須としない。
- 実装を複雑化させる機能は段階的に追加する。

# 2. システム構成

## 2.1 システム概要

本サービスは、以下の主要コンポーネントによって構成する。

| コンポーネント      | 責務                                   |
| ------------------- | -------------------------------------- |
| Timeline Engine     | タイムラインの解析・実行・時間管理     |
| Script Parser       | スクリプトの読み込み・構文解析         |
| Script Validator    | スクリプトの検証                       |
| Speech Manager      | 音声エンジンの管理・切り替え           |
| Web Speech Provider | ブラウザ標準TTS                        |
| VOICEVOX Provider   | VOICEVOX Engine連携                    |
| Audio Manager       | 音声ファイルの管理・再生               |
| Timeline UI         | タイムライン表示・操作                 |
| Storage Manager     | スクリプト・設定・音声キャッシュの保存 |

各コンポーネントは、可能な限り疎結合とする。

## 2.2 技術構成案

| 領域           | 技術候補                 |
| -------------- | ------------------------ |
| 開発言語       | TypeScript               |
| フロントエンド | React                    |
| ビルド         | Vite                     |
| スクリプト形式 | YAML / JSON              |
| スキーマ検証   | Zod                      |
| 時間計測       | Performance API          |
| 音声読み上げ   | Web Speech API           |
| 音声再生       | Web Audio API            |
| ローカル保存   | IndexedDB / localStorage |
| デプロイ       | 静的Webホスティング      |
| バックエンド   | 初期段階では不要         |

技術選定は確定事項ではなく、PoCの結果を踏まえて最終決定する。

# 3. 機能要件

優先度は以下の3段階で定義する。

- **P0：** MVPで必須
- **P1：** 初期リリース後に対応したい機能
- **P2：** 将来的な拡張

## 3.1 タイムライン管理

### FR-001 タイムライン読み込み【P0】

ユーザーが作成したタイムラインスクリプトを読み込めること。

対応する入力方法は以下とする。

- ローカルファイルからの読み込み
- テキストの直接入力
- サンプルタイムラインの読み込み

対応形式は以下とする。

- YAML
- JSON

両形式は同一の内部データ構造へ変換する。

### FR-002 スクリプト検証【P0】

読み込んだスクリプトに対して、以下の検証を行う。

- スキーマバージョン
- 必須項目の存在
- データ型
- 時刻指定の妥当性
- フェーズIDの重複
- イベントIDの重複
- 参照先フェーズの存在
- 不正な通知設定
- サポート対象外の構文

不正なスクリプトの場合、読み込みを中断し、修正可能なエラーメッセージを表示する。

### FR-003 タイムライン一覧表示【P0】

読み込んだタイムラインを時系列で表示する。

表示する情報は以下とする。

- 発生時刻
- ギミック名
- コール内容
- 事前通知時刻
- 所属フェーズ
- 実行済み・未実行の状態

### FR-004 タイムライン編集【P1】

Web画面上でタイムラインを編集できること。

編集対象は以下とする。

- イベント名
- 発生時刻
- コール内容
- 事前通知秒数
- フェーズ
- 音声通知の有効・無効

### FR-005 エクスポート【P0】

現在のタイムラインをJSONまたはYAMLとしてエクスポートできること。

エクスポートしたスクリプトは、再度読み込んで利用できること。

---

## 3.2 タイムライン実行

### FR-101 再生・停止【P0】

以下の操作に対応する。

- 再生開始
- 一時停止
- 再開
- 停止
- 先頭から再実行

停止時には、未実行のコールをキャンセルする。

一時停止時には時間の進行を停止する。

### FR-102 時間管理【P0】

タイムラインの経過時間を高精度に管理する。

要件は以下とする。

- 経過時間は単調増加時計を基準とする。
- `setInterval` の実行回数に依存しない。
- 描画処理と時間管理を分離する。
- タイマー処理の遅延を累積させない。
- スリープ復帰などで大きな時間差が発生した場合は、再同期を促す。

### FR-103 事前コール【P0】

イベントの発生時刻より前に、指定秒数だけ先行して通知できること。

例：

イベント発生時刻：60秒
事前通知：5秒

実際のコール時刻：55秒

事前通知秒数はイベント単位で設定可能とする。

### FR-104 フェーズ管理【P0】

複数フェーズで構成されるタイムラインに対応する。

各フェーズは以下の情報を保持する。

- フェーズID
- フェーズ名
- 所属イベント
- 開始時刻または開始条件

フェーズ開始方法は以下を想定する。

- 全体タイムラインに従った自動遷移
- ユーザーによる手動遷移

### FR-105 時間補正【P0】

手動操作による時間補正に対応する。

以下の操作を提供する。

- 指定秒数だけ進める
- 指定秒数だけ戻す
- 指定時刻に移動する
- 指定フェーズの開始位置に移動する

補正後、実行予定のイベントを再計算する。

時間補正によって過去のイベントが再実行されないよう、実行済み状態を管理する。

### FR-106 タイムライン分岐【P1】

任意の条件に基づき、タイムラインの進行先を変更できること。

初期対応では、ユーザーが手動で分岐先を選択する方式とする。

例：

- パターンA
- パターンB
- 特定フェーズへ移動

ゲームデータを利用した自動分岐は実装しない。

### FR-107 ループ処理【P1】

繰り返し発生するイベントに対応する。

スクリプト内で繰り返し回数と周期を定義できること。

無限ループや異常なイベント増殖を防ぐため、展開件数・繰り返し回数には制限を設ける。

# 4. 音声読み上げ

## 4.1 音声エンジン

### FR-201 Web Speech API【P0】

ブラウザ標準の音声合成機能を利用した読み上げを提供する。

以下の設定に対応する。

- 音声選択
- 読み上げ速度
- 音量
- ピッチ
- 読み上げテスト

利用可能な音声はブラウザおよびOSの環境に依存する。

### FR-202 VOICEVOX連携【P1】

ユーザーのローカル環境で動作するVOICEVOX Engineとの連携に対応する。

主な機能は以下とする。

- ローカルVOICEVOX Engineの接続確認
- 利用可能な話者・スタイルの取得
- 話者の選択
- 読み上げ速度の変更
- 音声の生成
- 生成した音声の再生

VOICEVOX Engineとの通信は、原則としてユーザーのブラウザから直接実行する。

接続できない場合には、適切なエラーを表示する。

### FR-203 音声の事前生成【P1】

タイムライン内のコールを事前に音声合成できること。

処理の流れは以下とする。

1. スクリプトを読み込む。
2. コール内容を抽出する。
3. 重複するコールを除外する。
4. 音声合成を実行する。
5. 生成音声を保存する。
6. 実行時に保存済み音声を再生する。

VOICEVOX利用時は、事前生成を基本とする。

### FR-204 音声キャッシュ【P1】

生成済み音声をクライアント側にキャッシュできること。

キャッシュキーには以下を含める。

- コール文章
- 音声エンジン
- 話者・スタイル
- 読み上げ速度
- ピッチなどの合成設定
- 必要に応じてエンジンバージョン

同じ設定の音声については、再生成を避ける。

### FR-205 コールの競合制御【P0】

複数のコールが連続する場合の動作を制御する。

対応する基本動作は以下とする。

- 新しいコールで前のコールを中断
- コールを順番に再生
- 優先度の低いコールを破棄

MVPでは、標準動作を「新しいコールで前のコールを中断」とする。

実行済みイベントを無制限にキューへ蓄積しないこと。

### FR-206 音声出力テスト【P0】

戦闘開始前に、選択した音声エンジンでテスト再生できること。

# 5. 画面表示

## 5.1 メイン画面

### FR-301 現在の進行状況【P0】

以下の情報を表示する。

- 現在の経過時間
- 現在のフェーズ
- 次のイベント
- 次のイベントまでの残り時間

イベント発生までの残り時間をリアルタイムに更新する。

### FR-303 実行済みイベント表示【P0】

### FR-304 画面レイアウト【P1】

以下の表示モードを提供する。

- 通常表示
- コンパクト表示

コンパクト表示は、将来的なオーバーレイ対応を意識したものとする。

# 6. スクリプト仕様

## 6.1 基本仕様

スクリプトは宣言的データとして扱う。

任意のJavaScriptやOSコマンドは実行しない。

スクリプトの構造は以下を基本とする。

- メタデータ
- フェーズ定義
- イベント定義
- 通知設定

## 6.2 スクリプト例

```yaml
version: 1

metadata:
  id: example-ultimate
  name: "絶コンテンツ サンプル"
  description: "タイムラインのサンプル"
  author: "Example"
  language: ja-JP

phases:
  - id: phase1
    name: "フェーズ1"
    start:
      type: absolute
      at: 0

    events:
      - id: raidwide-1
        at: 15
        name: "全体攻撃"
        notifications:
          - type: speech
            before: 5
            text: "5秒後、全体攻撃"

      - id: spread-1
        at: 30
        name: "散開"
        notifications:
          - type: speech
            before: 3
            text: "散開準備"

  - id: phase2
    name: "フェーズ2"
    start:
      type: absolute
      at: 90

    events:
      - id: tankbuster-1
        at: 10
        name: "タンク強攻撃"
        notifications:
          - type: speech
            before: 5
            text: "タンク強攻撃"
```

## 6.3 時刻の扱い

時刻は秒単位で定義する。

小数によるミリ秒精度の指定を許可する。

例：

`at: 10.5`

これは基準時刻から10.5秒後を意味する。

フェーズ内のイベント時刻は、そのフェーズの開始時刻を基準とする。

全体タイムラインの時刻とフェーズ内の相対時刻を区別して管理する。

## 6.4 スキーマバージョン

スクリプトには必ずバージョンを付与する。

将来の仕様変更に備え、旧バージョンからのマイグレーションを検討可能な構造とする。

# 7. 非機能要件

## 7.1 パフォーマンス

### NFR-001 タイマー精度

タイムラインの論理時刻は、実時間に対して累積的なドリフトを発生させない設計とする。

ただし、ブラウザのスケジューリングやOSの負荷による遅延は発生し得る。

PoCでは、少なくとも以下を計測する。

- イベント発火時刻の誤差
- 音声再生開始時刻の誤差
- バックグラウンド動作時の誤差
- 長時間連続実行時の誤差

音声再生の許容誤差は、PoCの結果を踏まえて設定する。

### NFR-002 クライアント負荷

通常のタイムライン再生時に、CPU負荷が過度に増加しないこと。

音声合成処理と再生処理を分離する。

### NFR-003 サーバー負荷

初期リリースでは、タイムライン実行にサーバー処理を必要としない。

---

## 7.2 セキュリティ

### NFR-101 スクリプト実行制限

外部スクリプトに含まれる任意コードを実行しない。

不正なデータ構造や過大なデータによって、ブラウザが停止しないよう対策する。

### NFR-102 ローカルAPIアクセス

VOICEVOX連携において、ユーザーが明示的に設定したローカルエンジンへのアクセスのみ許可する。

外部ホストへの任意リクエストをスクリプトから実行できないこと。

### NFR-103 データ保護

初期リリースでは、タイムラインや設定を原則としてローカルに保存する。

ユーザーの同意なしにスクリプト内容を外部送信しない。

---

## 7.3 可用性

### NFR-201 オフライン対応

初回読み込み後、主要機能をオフラインで利用できる構成を目指す。

ただし、利用する音声エンジンに応じて制約が生じる場合がある。

### NFR-202 エラー復旧

以下の事象に対して適切なエラー処理を行う。

- 不正なスクリプト
- 音声エンジンの初期化失敗
- 音声生成の失敗
- VOICEVOXへの接続失敗
- 音声再生の失敗
- ブラウザのスリープ・復帰
- 保存領域の不足

---

- 音声速度
- 音量

# 9. 将来拡張

## 9.1 オーバーレイ対応【P2】

Windowsなどのデスクトップ環境で、ゲーム画面上にタイムラインを表示する機能を検討する。

候補技術：

- Tauri
- WebView
- デスクトップ向けウィンドウ管理API

ただし、オーバーレイはFF14の外部ツールに関する規約上の懸念があるため、実装・提供の可否は別途判断する。

## 9.2 タイムライン共有【P2】

ユーザーが作成したタイムラインを共有できる機能を検討する。

想定機能：

- スクリプトのアップロード
- 公開・非公開設定
- URLによる共有
- バージョン管理
- 更新履歴
- インポート

初期リリースではローカルファイルによる共有を基本とする。

## 9.3 他音声エンジン対応【P2】

将来的にVOICEVOX以外の音声エンジンを追加できるよう、音声管理部分を抽象化する。

## 9.4 プリセット提供【P2】

ユーザーが簡単に利用できるタイムラインプリセットを提供する。

配布するスクリプトやコンテンツに関する権利関係は別途確認する。

# 11. MVP定義

## 11.1 MVPの目的

最小限の実装で、スクリプトに従ったタイムラインの実行と音声コールが実用的に動作することを検証する。

## 11.2 MVP対象機能

| 機能                    | MVP |
| ----------------------- | --- |
| JSON/YAML読み込み       | ○   |
| スクリプト検証          | ○   |
| タイムライン表示        | ○   |
| 再生・停止・一時停止    | ○   |
| 指定秒数でのコール      | ○   |
| 事前コール              | ○   |
| フェーズ管理            | ○   |
| 手動時間補正            | ○   |
| Web Speech API          | ○   |
| 読み上げテスト          | ○   |
| JSON/YAMLエクスポート   | ○   |
| VOICEVOX連携            | ×   |
| VOICEVOX音声キャッシュ  | ×   |
| GUIによるスクリプト編集 | ×   |
| 条件分岐                | ×   |
| ループ処理              | ×   |
| オーバーレイ            | ×   |

VOICEVOX連携はMVP検証後の優先実装候補とする。

## 11.3 MVP完了条件

以下を満たすこと。

1. ユーザーが独自のタイムラインを読み込める。
2. スクリプトに従ってイベントが実行される。
3. 指定されたタイミングで音声コールが行われる。
4. フェーズ切り替えと手動時間補正ができる。
5. 30分以上の連続実行で、タイマーに累積ドリフトが生じない。
6. 音声が重複した際に、設定した競合制御が機能する。
7. ゲームクライアントとの連携を必要としない。
8. データの保存・再読み込みができる。

# 12. 技術検証項目

本格開発前に、以下のPoCを実施する。

## PoC-001 タイマー精度

ブラウザで30分以上のタイムラインを実行する。

通常表示、バックグラウンド表示、それぞれの条件で精度を測定する。

## PoC-002 Web Speech API

連続した読み上げにおける遅延や競合を検証する。

特に短時間に複数コールが発生した場合の挙動を確認する。

## PoC-003 VOICEVOX連携

HTTPSで提供するWebアプリから、ローカルのVOICEVOX Engineへ接続できるか検証する。

CORS、Private Network Access、ブラウザのローカルネットワークアクセス制限などを確認する。

## PoC-004 音声キャッシュ

事前生成した音声をIndexedDBへ保存し、指定時刻に再生できるか検証する。

音声のデコードや再生開始時に発生する遅延を確認する。

# 16. 成功基準

本プロジェクトの初期段階では、収益化やユーザー数を主要な成功基準としない。

まずは以下を目標とする。

- 作成したタイムラインを問題なく再生できること
- 利用者がコール内容・タイミングを自由に調整できること
- 通常の利用環境で安定して音声通知ができること
- 実際の利用者から改善要望やフィードバックを得られること
- 開発・運用コストを低く維持できること

**最終的には、利用者が自分の用途に合わせてタイムラインを構築し、安心して利用できる汎用的な音声通知プラットフォームを目指す。**
