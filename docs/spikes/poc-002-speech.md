# PoC-002 Web Speech (結果)

手順と合否の目安は [08-poc](../design/08-poc.md)、計測ページは `spikes/poc-002-speech/`。

## 1 回目 (2026-10-11)

| 端末・ブラウザ                           | 声                                 | 測ったもの                        |
| ---------------------------------------- | ---------------------------------- | --------------------------------- |
| Windows、Chrome 154                      | Microsoft Ayumi (日本語、端末の声) | A 50 回、B 中断 5 回、C 0ms 20 回 |
| iPhone、Brave (WebKit、Safari 26.6 相当) | ブラウザの既定                     | D 20 秒ごと 25 回 (約 8 分)       |

**PC の A・B・C は同時に走っていた** (A 860〜1058 秒、B 863〜903 秒、C 872〜919 秒。計測ページが同時に始められる作りだった)。読み上げはブラウザに 1 つしか無いので、B と C の `cancel()` が A の読み上げを止め、A の読み上げが B と C の待ち行列に入っていた。B と C の数字と、A の最初の 12 回は使えない。ページは 1 つずつしか回せないように直した。

### A 立ち上がり (PC、B と C が終わった後の 38 回だけ)

| 声                     | 回数 | 失敗 | p50    | p95    | 最大   |
| ---------------------- | ---- | ---- | ------ | ------ | ------ |
| Microsoft Ayumi (端末) | 38   | 0    | 14.4ms | 17.1ms | 18.7ms |

目安 (p95 ≤ 300ms) を大きく下回る。

### D 長く鳴らし続ける (iPhone)

| 回数 | 鳴った | 立ち上がり p50 | p95   | 最大  | タイマーの遅れ           |
| ---- | ------ | -------------- | ----- | ----- | ------------------------ |
| 25   | 25     | 320ms          | 322ms | 322ms | 1 回目 55ms、以降 1〜6ms |

- 画面を触らずに約 8 分、全部鳴った。Wake Lock も外れなかった (全件 visible)
- **立ち上がりが毎回ほぼ同じ 320ms** (ばらつき 5ms)。目安の 300ms を少し超えるが、一定なので、先に知らせる (`lookaheadMs`) ことで消せる

### 同時に走っていたことから分かったこと (参考)

- Chrome では、`cancel()` の直後に `speak()` した読み上げが、すぐ `interrupted` で止まることがある。B の中断で、最後のコールが話し始めてから 0.1〜1.3 秒で止まった回が 4/5。ただし A の読み上げが混ざっていたので、cancel の直後だけが原因とは言えない。C を 1 つずつ回して確かめる

## 2 回目 (2026-10-11、PC、1 つずつ)

Windows、Chrome 154、ブラウザの既定の声。計測を 1 つずつ回せるように直したページで測った。

### C cancel の直後 (0ms)

| 回数 | 次が鳴った | 立ち上がり p50 | p95  | 最大 |
| ---- | ---------- | -------------- | ---- | ---- |
| 20   | 20         | 59ms           | 67ms | 73ms |

- cancel の直後に間を空けずに話しても、落ちなかった。1 回目に落ちたのは、A と B が同時に走っていたため
- cancel の直後は、ふだん (15ms 前後) より 45ms ほど遅く話し始める。事前コールに比べて小さい
- 0ms で落ちないので、100ms は測っていない

### B 中断、間隔 1 秒

| 回数 | 3 つとも話し始めた | 最後のコール (3) が最後まで鳴った | 中断から次の話し始めまで |
| ---- | ------------------ | --------------------------------- | ------------------------ |
| 5    | 5                  | 5                                 | 30〜67ms                 |

- 中断された読み上げの `interrupted` の知らせは、毎回、次の読み上げを始めた後に届く。Call Arbiter はこれを古いコールの知らせとして読み捨て、新しいコールを止めなかった (`arbiter.test.mjs` の「callbacks from an interrupted call do not end the new call」と同じ動き)

## まだ分からないこと

- iPhone の C (cancel の直後) と B
- B の順番と優先度を単独で回したときの動き (Call Arbiter のテストでは確かめてある)
- iPhone の A (立ち上がりが 320ms で一定なのは、D の短い文だけか)
- Edge のオンラインの声 (Natural)

## 判断

- **競合の既定は「中断」のまま** (要件 FR-205)。PC の Chrome で、最後のコールが 5 回とも最後まで鳴った
- **cancel の後に間は要らない** (`restartDelayMs` は 0)。PC の Chrome で 20 回とも落ちなかった。iPhone で落ちる回があれば、そのとき見直す
- 中断された読み上げの知らせは遅れて届くので、プロバイダの知らせは「どのコールのものか」を見て、今のコールでなければ読み捨てる (Call Arbiter の作り)

## いまの考え (仮)

- Web Speech の立ち上がりは端末で大きく違う (PC 15ms、iPhone 320ms) が、同じ端末の中ではほぼ一定。設定画面の「テスト再生」で立ち上がりを測り、その値を `lookaheadMs` としてエンジンに渡す案がよさそう (04、03)
